# 两个完整 case 的性能分析

日期：2026-09-08。输入是刚完成的编程课和数学课；本次没有重跑整课，也没有修改供用户评审的讲义。

## 主要结论

目前最大的耗时来源是**串行云端请求**。编程课已计时阶段中 87.5% 在图文或 ASR 请求内，数学课为 78.8%。这些数值包含上传、服务等待、推理及接收响应，不能全部叫作“模型思考时间”。只优化本地 Markdown 渲染不能解决主要等待。

| 阶段 | 编程课（约 100 分钟） | 数学课（约 45 分钟） |
| --- | ---: | ---: |
| 已记录阶段合计 | 32 分 00 秒 | 14 分 55 秒 |
| 语音转写 | 7 分 42 秒 | 4 分 17 秒 |
| 截图采样 | 2 分 05 秒 | 2 分 33 秒 |
| 图文组织，含修复 | 21 分 20 秒 | 8 分 01 秒 |
| 校验与导出 | 53 秒 | 4 秒 |

阶段表不重复叠加嵌套请求，也不包含旧日志未计时的预检、阶段间清单写入和最终提交。两个任务独立运行，不能将两列相加当作用户等待时间。

## 已定位的问题

1. **章节请求串行。** 编程课 34 章实际调用图文模型 44 次，请求内累计 1259.7 秒；数学课 15 章调用 18 次，累计 475.8 秒。应用层逐章等待完成后才开始下一章。
2. **格式失败产生额外请求。** 编程课 10 次失败请求累计 194.0 秒，其中 9 次原始输出是空数组，另一次未通过语义约束；数学课 3 次空数组请求累计 90.3 秒。即使消除这些失败，每个 case 也只减少约 10% 的已计时阶段，仍需处理成功请求的串行等待。
3. **ASR 有少量长尾请求。** 编程课单次中位数 1.30 秒、P95 1.75 秒，但开头 4 次超过 10 秒，累计 157.0 秒；数学课中位数 1.47 秒、P95 1.88 秒，首次请求 99.25 秒。现有记录不足以区分上传、排队或服务内部原因，不能把全部长尾时间算作可消除开销。
4. **候选帧被重复解码和编码。** 采样先解码画面做差异判断，保留时 `register_frame` 再解码一次。120 秒回放中，12 个扫描时刻分别触发 17 次（编程）和 16 次（数学）解码；保留 5/4 张候选却做了 10/8 次 PNG 保存。没有裁剪时原图与选中图仍各编码一遍。
5. **导出长尾尚未复现。** 编程课原运行校验导出 52.7 秒，本地回放中整份讲义校验 1.72 秒、渲染 0.118 秒、导出 3.62 秒。当前导出回放主要耗在文件打开和图片检查，未证明渲染算法造成了之前的长尾。没有控制系统负载和冷缓存，不推断是磁盘或防病毒软件的具体问题。

## 实际 profiling 方法

新增开发工具 [profile_conversion.py](../tools/profile_conversion.py)，使用 Python 标准库 `cProfile`、`pstats`，不增加运行依赖，不新增产品 CLI 命令。它先分析原始日志；加 `--local` 后，以原课中间 120 秒回放音频准备及截图采样，并对整份已生成讲义回放校验、渲染、导出。所有回放写入新的报告目录，已有输出只读。

```powershell
uv run python tools/profile_conversion.py output/programming-full output/math-full --report-dir artifacts/profiling/my-run --local
```

报告目录必须是新目录，不能与原转换目录或素材目录重叠。省略 `--local` 只分析日志；`--sample-seconds` 可取 30、60、120、300。每个步骤输出墙钟时间、进程 CPU 时间、`.prof` 文件和累计耗时前 25 项的 `.txt`。

| 本地回放操作 | 编程课墙钟 | 数学课墙钟 |
| --- | ---: | ---: |
| 120 秒音频解码与 WAV 编码 | 0.972 秒 | 1.380 秒 |
| 120 秒截图采样与登记 | 2.397 秒 | 16.942 秒 |
| 整份讲义校验 | 1.720 秒 | 4.466 秒 |
| 整份 Markdown 渲染 | 0.118 秒 | 0.005 秒 |
| 整份讲义导出到新目录 | 3.620 秒 | 2.575 秒 |

这是一次带 cProfile 开销、未控制缓存的本地回放，不是新的整课性能基准。数学采样的累计热点为抽帧 12.16 秒、PNG 保存 3.64 秒；累计时间存在调用嵌套，不能随意相加。回放前后原 `notes.md` 与 `notes.json` 哈希一致。

原始数据在 `artifacts/profiling/full-cases-20260908/`，其 `report.md` 与 `summary.json` 提供完整统计，各 case 子目录含逐函数报告。

## 新增可观测性与一次云端探测

后续事件增加 `run_id`、UTC 时间和本次操作的相对秒数；图文请求记录章节、尝试次数、证据打包时间与字节数、失败耗时和原始响应 ID。Qwen 流另记录打开流、首块、首段思考、首段正文以及整体结束时间，原始思考文本不保存。

本次只复用编程课 `ch-002` 发出 **1 次**独立计时请求，不做重试。证据打包 0.016 秒，10 张图共 3.60 MB；首块及首段思考均约 4.609 秒到达，随后供应商内容检测在约 7.063 秒中止响应，没有正文。该探测只验证了部分计时，**不能代表成功请求的生成速度，也不能据此比较思考开关**。记录位于 `artifacts/profiling/cloud-probe-20260908/`。

探测暴露的流内通用 API 错误现在会记录耗时并以受控错误结束，不回显服务原始消息、不自动重试。计时、失败路径和旧日志汇总均有离线回归检查。

## 后续优化顺序

- 优先查清空数组输出的触发条件并减少格式修复请求；保留 schema 与证据校验，不能靠放松校验换速度。
- 在独立实验中测量 2–4 个章节请求的有界并发；仍由单一写入者按序发布结果，统一调用预算，并检查服务限流。收益尚未实测。
- 对相同证据比较思考开关与输出质量，用首正文延迟及完成时间衡量；不只比较模型名或单次总时间。
- 复用已解码的候选帧，无裁剪时复用 PNG 编码结果，减少已确认的本地重复工作。

本轮交付是性能定位、可复用分析工具和计时补充，没有改变并发、思考默认值、采样策略或内容生成流程；尚未声称转换已加速。
